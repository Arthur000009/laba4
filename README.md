# Лабораторная работа № 4. Сервис доставки

Продолжение [лабораторной работы № 3](https://github.com/Arthur000009/laba3).
К REST API добавлены HTTP Basic, CSRF-защита, регистрация пользователей,
роли CLIENT и DISPATCHER, блокировка аккаунтов и проверка владельца отправления.

Стек: Java 21, Spring Boot 4.1.1, Spring Security, Spring Data JPA,
PostgreSQL и Maven Wrapper.

## Подготовка базы данных

Для проекта используется отдельная база `courier_lab4`.
Её можно создать в pgAdmin с владельцем `postgres` или командой:

```powershell
createdb -h localhost -p 5432 -U postgres courier_lab4
```

Из корня проекта выполните:

```powershell
psql -h localhost -p 5432 -U postgres -d courier_lab4 -v app_password='replace-with-your-database-password' -f init.sql
```

Замените значение `app_password` своим паролем пользователя базы данных.
Команды `createdb` и `psql` должны быть доступны в PATH.

Скрипт `init.sql` удаляет и создаёт таблицы заново. Используйте его только
для отдельной базы этой лабораторной. Для обычного повторного запуска
приложения выполнять скрипт не нужно.

Скрипт содержит команды `psql`, поэтому его следует запускать через
`psql`, а не через Query Tool в pgAdmin.

Создаются пять предметных таблиц: `users`, `routes`, `stops`,
`shipments`, `shipment_assignments`. Таблица `operation_guard`
содержит служебную строку для блокировки операций записи.

Приложение подключается под пользователем `courier_lab4_app`.
У него есть права на работу с данными и последовательностями, но нет
прав суперпользователя, создания баз, ролей и таблиц.
Hibernate проверяет готовую схему через `ddl-auto: validate`.

## Настройка и запуск

Нужна JDK 21. Отдельно устанавливать Maven не требуется:
используется Maven Wrapper из проекта.

Скопируйте файл настроек:

```powershell
Copy-Item .env.example .env
```

В `.env` задайте:

- `DB_URL` — адрес базы, по умолчанию `jdbc:postgresql://localhost:5432/courier_lab4`;
- `DB_USERNAME` — `courier_lab4_app`;
- `DB_PASSWORD` — пароль, переданный в `app_password` при запуске SQL-скрипта;
- `APP_BOOTSTRAP_ENABLED=true` — для первоначального создания диспетчера;
- `APP_DISPATCHER_EMAIL` и `APP_DISPATCHER_PASSWORD` — учётные данные диспетчера;
- `COOKIE_SECURE=false` — для локального запуска по HTTP.

Пароль диспетчера должен содержать минимум 12 символов, прописную и
строчную букву, цифру и спецсимвол. Максимальная длина — 72 байта UTF-8.
Заглушки из `.env.example` нужно заменить.

Сборка в Windows:

```powershell
.\mvnw.cmd clean package
```

Запуск в Windows:

```powershell
.\mvnw.cmd spring-boot:run
```

В Linux и macOS используются `./mvnw clean package` и
`./mvnw spring-boot:run`. При необходимости выполните `chmod +x mvnw`.

Также приложение можно запустить в IntelliJ IDEA через
`DostavkaApplication`, выбрав JDK 21 и корень проекта в качестве
рабочей папки.

Адрес приложения: `http://localhost:8080`.

При первом запуске `BootstrapDispatcher` создаёт диспетчера.
После успешного создания установите в `.env`:

```properties
APP_BOOTSTRAP_ENABLED=false
```

Аккаунт останется в базе. Повторное включение bootstrap не меняет
пароль существующего диспетчера и не повышает роль существующего клиента.

## Проверка через Postman

1. Импортируйте `postman_collection.json`.
2. В переменных коллекции задайте локальные значения
   `dispatcherEmail` и `dispatcherPassword` из настроенной учётной записи.
3. Проверьте `baseUrl`: `http://localhost:8080`.
4. Оставьте Cookie Jar включённым.
5. Запустите всю коллекцию сверху вниз, одна итерация.

Первый запрос получает CSRF-токен и cookie сессии.
Скрипты коллекции сохраняют токен и ID созданных объектов.
Для клиентов создаются уникальные email, поэтому коллекцию можно
запускать повторно.

В коллекции 82 запроса и 187 проверок ответов. Проверяются регистрация,
аутентификация, права доступа, владение объектами, блокировка клиента,
CRUD и бизнес-операции. Отрицательные сценарии ожидают ошибки
`400`, `401`, `403` или `409`.

Результат локального прогона 31.10.2026 с PostgreSQL 17.11:
187 Passed, 0 Failed, 0 Errors, 0 Skipped.

`clientPassword` содержит пароль учебных аккаунтов.
Пароль диспетчера в файле коллекции пустой; его нужно задать локально.

В рамках одного прогона используйте один хост: `localhost` и
`127.0.0.1` считаются разными хостами для cookie.
После истечения сессии получите новый CSRF-токен.

## Аутентификация и CSRF

Логин пользователя — email. При сохранении он приводится к нижнему
регистру; уникальность проверяется в сервисе и в базе данных.

Пароли хранятся в виде BCrypt-хешей со стоимостью 12.
На каждом защищённом запросе HTTP Basic проверяет учётные данные
и состояние аккаунта. Сессия не заменяет аутентификацию.

`GET /api/csrf` доступен без аутентификации и возвращает
`token`, `headerName`, `parameterName`.

Запросы, изменяющие данные, включая регистрацию, должны содержать
заголовок `X-CSRF-TOKEN` и cookie `JSESSIONID` той же сессии.
Отсутствующий или неверный токен приводит к `403 CSRF_INVALID`.

Публичная регистрация: `POST /api/auth/register`.

```json
{
  "name": "Иван",
  "email": "ivan@example.com",
  "password": "MyLearningPass1!"
}
```

`GET /api/auth/me` с HTTP Basic возвращает текущего пользователя.

При размещении приложения по HTTPS задайте `COOKIE_SECURE=true`.
HTTP Basic сам по себе не шифрует передаваемые учётные данные.

## Роли и доступ

Роли: `CLIENT` и `DISPATCHER`.
Состояния аккаунта: `ACTIVE` и `BLOCKED`.
Заблокированный пользователь не проходит аутентификацию.

Регистрация и `POST /api/users` создают только активного клиента.
Назначить себе роль диспетчера или изменить хеш пароля через JSON нельзя.
Обновление профиля разрешает менять только имя и email.

| Операция | CLIENT | DISPATCHER |
|---|---|---|
| Список пользователей | Запрещено | Разрешено |
| Чтение и изменение профиля | Только свой | Любой |
| Создание пользователя через /api/users | Запрещено | Создание клиента |
| Блокировка и удаление пользователя | Запрещено | Только клиент; удаление без активных отправлений |
| Список и чтение отправлений | Только свои | Все |
| Создание отправления | От своего имени | Для указанного активного клиента |
| Изменение отправления | Своё в CREATED | Любое в CREATED |
| Удаление отправления | Своё, кроме IN_TRANSIT | Любое, кроме IN_TRANSIT |
| CRUD маршрутов, остановок, назначений | Запрещено | С учётом бизнес-ограничений |
| Назначение, запуск, доставка, перенос | Запрещено | С учётом бизнес-ограничений |
| Отмена отправления | Своё до отправки | Любое до отправки |

Клиент может не передавать `senderId`: сервер использует ID
аутентифицированного пользователя. Диспетчер указывает ID клиента.

Доступ к группам URL ограничивает `SecurityFilterChain`.
Аннотации `@PreAuthorize` и `AccessControl` проверяют роль и владельца.
Для клиента чтение чужого и несуществующего отправления даёт одинаковый
ответ `403`. Через API нельзя блокировать или удалять диспетчера.

## DTO и структура проекта

`Requests.java` задаёт поля входящих запросов.
Неизвестные поля отклоняются с `400 INVALID_REQUEST`.

`Responses.java` задаёт состав ответов API. Например, `UserResponse`
содержит `id`, `name`, `email`, `role`, `accountStatus`.
Поля `passwordHash` в нём нет. `DtoMapper` преобразует сущности в DTO.
Аннотация `@JsonIgnore` на хеше в `User` сохранена как дополнительная защита.

Основной код находится в `src/main/java/com/example/dostavka`:

- `controllers` — HTTP-эндпоинты, преобразование DTO и обработка ошибок;
- `dto` — структуры запросов и ответов;
- `models` — JPA-сущности и перечисления;
- `repositories` — доступ к данным через Spring Data JPA;
- `services` — бизнес-правила и транзакции;
- `security` — аутентификация, роли, CSRF и политика паролей.

## CRUD и бизнес-операции

Ресурсы: `/api/users`, `/api/routes`, `/api/stops`,
`/api/shipments`, `/api/shipment-assignments`.

Для каждого ресурса реализованы получение списка, получение по ID,
создание, изменение и удаление — всего 25 CRUD-эндпоинтов.

| Операция | Метод и путь |
|---|---|
| Назначение отправления | POST /api/routes/{routeId}/assign-shipment?stopId=...&shipmentId=... |
| Запуск маршрута | POST /api/routes/{routeId}/start |
| Доставка на остановке | POST /api/stops/{stopId}/deliver |
| Перенос отправления | POST /api/shipments/{shipmentId}/transfer?newStopId=... |
| Отмена отправления | POST /api/shipments/{shipmentId}/cancel |

Назначение требует маршрута в PLANNED, отправления в CREATED,
совпадения адресов и соблюдения ограничения веса.

Запуск переводит маршрут в IN_PROGRESS, а назначенные отправления —
в IN_TRANSIT. Доставка выполняется по порядку остановок, на которых
есть назначения. После доставки всех назначенных отправлений
маршрут получает COMPLETED.

Перенос возможен для ASSIGNED между остановками планируемых маршрутов
с проверкой адреса и вместимости. Отмена разрешена для CREATED и ASSIGNED.

Удалять маршруты, остановки и назначения можно только до запуска
маршрута. При удалении назначения отправление возвращается в CREATED.
Отправление в IN_TRANSIT удалить нельзя.

Операции записи выполняются в транзакциях.
`DomainLock` блокирует строку `operation_guard(id=1)` до завершения
транзакции. Это предотвращает одновременное изменение связанных
состояний, но последовательно выполняет все операции записи.

## Ошибки API

| HTTP | code | Причина |
|---|---|---|
| 400 | INVALID_REQUEST | Некорректные данные, неизвестные поля, слабый пароль |
| 401 | UNAUTHENTICATED | Нет действительных учётных данных |
| 403 | FORBIDDEN | Недостаточно прав или чужой объект |
| 403 | CSRF_INVALID | Нет корректного CSRF-токена и соответствующей сессии |
| 404 | — | Разрешённое чтение или изменение отсутствующего объекта |
| 405 | INVALID_REQUEST | HTTP-метод не поддерживается для этого адреса |
| 409 | BUSINESS_CONFLICT | Нарушение бизнес-ограничений |
| 409 | DATA_CONFLICT | Нарушение уникальности или целостности данных |
| 409 | CONCURRENT_MODIFICATION | Конфликт блокировки |
| 415 | INVALID_REQUEST | Неподдерживаемый формат тела запроса |
| 500 | INTERNAL_ERROR | Неожиданная внутренняя ошибка |

Обработанные ошибки возвращаются с полями `code` и `message`.
Ответы 404 при отсутствии объекта формируются без тела.
SQL, стек исключения, пароли и хеши в ошибки не включаются.

CSRF проверяется раньше HTTP Basic. Запрос, изменяющий данные, без
токена может получить 403 раньше проверки логина и пароля.
Для демонстрации 401 используйте защищённый GET или корректный CSRF.
